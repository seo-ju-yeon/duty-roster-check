# 데이터 구조와 검사 기준 초안

모든 기준은 학습용 가정입니다. 규칙 버전과 기간·연속 근무 제한의 원본은 `config.toml`입니다.
여기서는 그 설정의 의미를 설명합니다. 날짜·근무조별 최소 인원의 원본은 `requirements.csv`입니다.

## 행의 의미

모든 입력 CSV는 UTF-8, 쉼표 구분, 첫 행에 열 이름을 둡니다.
ID는 문자열, 날짜는 정확한 `YYYY-MM-DD` 형식의 존재하는 날짜, 근무 상태는 대문자로 기록합니다.
빈 값, 앞뒤 공백, 다른 대소문자를 임의로 보정하지 않습니다.
필수 열 누락·중복 열 이름·행별 열 개수 불일치는 입력 오류입니다. 추가 열은 첫 버전에서 허용하되 검사에는 사용하지 않습니다.

| 파일 | 열 | 한 행의 의미 | 작은 자료 | 대표 자료 |
| --- | --- | --- | --- | --- |
| nurses.csv | nurse_id | 기준 목록의 간호사 한 명 | 4행 | 12행 |
| schedule.csv | nurse_id, date, shift | 간호사 한 명의 특정 날짜 상태 | 12행 | 168행 |
| requirements.csv | date, shift, min_staff | 날짜·근무조의 최소 필요 인원 | 9행 | 42행 |
| unavailability.csv | nurse_id, date | 해당 간호사가 근무할 수 없는 하루 | 1행 | 추후 작성 |

휴무 O도 schedule에 반드시 한 행으로 기록합니다. 행이 없으면 휴무가 아니라 입력 누락입니다.
unavailability에 없는 간호사·날짜는 **근무 불가 제한이 등록되지 않은 날로서 배정 가능**하다고 가정합니다.
등록된 날은 O만 허용합니다. 이것은 가상 입력이 완전하게 제공됐다는 프로젝트 내부 가정입니다.
unavailability는 헤더만 있는 파일도 유효합니다. 나머지 입력은 필요한 기준 행을 갖춰야 합니다.

requirements는 모든 날짜의 D/E/N 조합을 0명인 경우까지 명시하며 O는 넣지 않습니다.
같은 날짜·근무조를 두 번 쓰거나 일부 조합을 생략하면 입력 오류입니다.
min_staff는 0 이상의 정수이며 기준 간호사 수 이하여야 합니다. `1.0`, 음수, 빈 값은 허용하지 않습니다.
개별 값이 범위 안이어도 여러 제약을 함께 만족하는 해가 반드시 있는 것은 아닙니다.

## 초기 값과 가능성 확인

| 항목 | 작은 테스트 | 대표 시연·분석 제안 |
| --- | --- | --- |
| 기간 | 2026-11-01~03, 양 끝 포함 | 2026-11-01~14, 양 끝 포함 |
| 인원 | N01~N04 | N01~N12 |
| 매일 최소 D/E/N | 1 / 0 / 1 | 3 / 2 / 2 |
| 최대 연속 근무 | 2일 | 5일 |
| 금지 전환 | N 다음 달력 날짜의 D | 동일 |
| 근무 불가 | N02, 2026-11-02 | N01, 2026-11-04 제안 |

작은 자료는 3일 안에서 연속 근무 초과를 보여 주려고 상한을 2로 둡니다.
4명 모두 3일 중 최대 2일만 일할 수 있으므로 가능한 총 근무는 최대 8건입니다.
매일 D/E/N 각각 1명이면 필요한 근무가 9건이므로 불가능합니다.
따라서 작은 자료의 E 최소 인원을 0으로 둡니다. E 배정은 가능하며 정상 후보에는 1건이 있습니다.
이는 대표 데이터의 최소 인원을 축소한 동일 문제가 아니라, 규칙을 확인하기 위한 별도 작은 문제입니다.

대표 제안의 해 존재 여부는 전체 CSV 생성 전에 다음 구성으로 설명할 수 있습니다.
N01~03, N04~06, N07~09, N10~12를 각각 3명씩 묶고 네 그룹이
`D E N O`, `E N O D`, `N O D E`, `O D E N`의 4일 주기를 반복한다고 가정합니다.
매일 D/E/N/O가 각각 3명으로 최소 3/2/2를 충족합니다. 연속 근무는 최대 3일이며 N 뒤에는 O가 옵니다.
N01은 11월 4일 O이므로 제안한 근무 불가 날짜도 지킵니다.
이 구성은 제안 조건의 가능성을 보이는 근거이며, 대표 데이터 파일 작성이나 생성기 실행 결과는 아닙니다.
추후 근무 불가 날짜 등을 바꾸면 가능성을 다시 확인합니다.

## 입력 오류 처리 순서

첫 버전은 **입력 오류가 있으면 모든 배정 규칙 검사를 보류**합니다.
잘못된 행을 삭제하거나 첫 중복 행만 선택해 계속 검사하지 않습니다.

1. 파일·헤더·행 구조를 확인합니다. 실패하면 해당 구조에 의존하는 검사는 `NOT_RUN`입니다.
2. 기준 목록과 값의 유효성, 날짜·근무 상태·숫자·참조를 확인합니다. 실패하면 완전성 검사를 보류합니다.
3. 값과 참조가 유효할 때 schedule의 간호사·날짜, requirements의 날짜·근무조,
   unavailability의 간호사·날짜에 대한 중복과 필수 조합 누락을 확인합니다.
4. 위 입력 검사를 모두 통과한 경우에만 배정 규칙을 검사합니다.

같은 단계에서 독립적으로 확인할 수 있는 오류는 모읍니다. 앞 단계 때문에 판단할 수 없는 오류는 추측하지 않습니다.
예를 들어 잘못된 간호사 ID가 있으면 참조 오류를 기록하고, 그로 인한 누락까지 연쇄 집계하지 않습니다.
중복 schedule 키는 입력 오류로 한 번만 출력합니다. 배정 규칙에서 다시 중복 집계하지 않습니다.

| 결과 항목 | 값 | 의미 |
| --- | --- | --- |
| input_status | VALID / INVALID | 입력 검사 통과 / 입력 오류 존재 |
| assignment_status | PASS / FAIL / NOT_RUN | 기간 내부 배정 검사 통과 / 위반 존재 / 입력 오류로 실행하지 않음 |
| assignment_issue_count | 정수 또는 빈 칸 | PASS는 0, FAIL은 사건 수, NOT_RUN은 빈 칸 |

파일을 읽지 못한 경우도 입력 오류로 보고합니다. 읽을 수 없는 형식 오류와
읽은 뒤 발견한 값·참조·완전성 오류는 `rule_id`로 구분합니다.
`NOT_RUN`을 위반 0건으로 표시하지 않습니다. 후속 분석도 첫 버전에서는 입력 오류가 있으면 보류합니다.
입력은 유효하지만 배정 위반이 있는 근무표는 위반을 보존한 채 분석할 수 있습니다.

## 입력 검사 목록

아래 이유 문장은 출력 예시입니다. 관련 파일과 가능한 경우 CSV 줄 번호를 함께 기록합니다.

| ID | 목적·필요한 입력 | 정상 / 오류 예 | 이유 예 | 판단을 보류할 조건 |
| --- | --- | --- | --- | --- |
| I_FILE_SCHEMA | 네 파일의 읽기·필수 열·행 구조 확인 | 필수 열 존재 / shift 열 없음 | schedule.csv에 shift 열이 없습니다 | 파일을 읽지 못하면 그 파일의 값 검사 보류 |
| I_REQUIRED_VALUE | 필수 열의 빈 값·공백 확인 | N01 / 빈 nurse_id | nurse_id 필수값이 없습니다 | 파일·열 구조 불명 |
| I_DATE | 모든 날짜 형식·존재 여부·기간 확인 | 2026-11-01 / 2026-11-31 또는 기간 밖 | date가 검사 기간 밖입니다 | 날짜 열을 읽을 수 없음 |
| I_SHIFT | schedule은 D/E/N/O, requirements는 D/E/N인지 확인 | schedule의 O / requirements의 O | requirements에는 O를 사용할 수 없습니다 | shift 값 누락·열 없음 |
| I_NURSE_LIST | nurses의 유일 ID·설정 인원수 확인 | 4개 서로 다른 ID / N01 반복 | 기준 간호사 ID N01이 중복입니다 | 기준 파일 구조 오류 |
| I_UNKNOWN_NURSE | schedule·unavailability의 ID 참조 확인 | N01 / N99 | N99는 기준 간호사 목록에 없습니다 | 기준 목록 자체가 유효하지 않음 |
| I_MIN_STAFF | 최소 인원 정수·범위 확인 | 0 또는 1 / -1 또는 1.5 | min_staff는 0 이상 간호사 수 이하의 정수여야 합니다 | 숫자 열 누락, 유효 간호사 수 미확정 |
| I_SCHEDULE_DUPLICATE | schedule의 간호사·날짜 유일성 확인 | 키당 1행 / N01·11-01 두 행 | 같은 간호사·날짜 기록이 2행입니다 | 앞 단계 값·참조 오류 |
| I_SCHEDULE_MISSING | nurses × 기간의 모든 상태가 있는지 확인 | O 한 행 / 행 자체 없음 | N01의 11-03 기록이 없습니다 | 앞 단계 값·참조 오류 |
| I_REQUIREMENTS_KEY | 날짜 × D/E/N 조합의 중복·누락 확인 | 9개 서로 다른 조합 / E 조합 누락 | 11-01 E 최소 인원 기록이 없습니다 | 앞 단계 값·참조 오류 |
| I_UNAVAILABILITY_DUPLICATE | 근무 불가 정보의 중복으로 표 연결이 늘어나는 것을 방지 | 키당 1행 / 같은 키 반복 | 근무 불가 날짜가 중복 등록됐습니다 | 앞 단계 값·참조 오류 |

## 배정 검사 목록

모든 배정 검사는 위 입력 검사를 통과했을 때만 수행합니다.
근무 상태 D/E/N을 근무일로 세며 O는 연속 근무를 끊습니다. 시간 단위 계산은 하지 않습니다.

| ID | 목적·필요한 입력 | 정상 / 위반 예 | 출력할 이유 | 판단할 수 없는 상황 |
| --- | --- | --- | --- | --- |
| R_UNAVAILABLE | schedule과 unavailability를 대조해 불가 날짜 근무 탐지 | 불가 날짜 O / E | 근무 불가 날짜에 E가 배정됐습니다 | 입력 오류 |
| R_MIN_STAFF | requirements의 모든 날짜·근무조를 실제 고유 간호사 수와 대조 | 실제 1 ≥ 최소 1 / 실제 0 < 최소 1 | 최소 1명이나 실제 0명으로 1명 부족합니다 | 입력 오류 |
| R_MAX_CONSECUTIVE | 간호사별 날짜를 정렬하고 연속된 달력 날짜의 근무 구간 확인 | D,D,O / D,D,E, 상한 2 | 11-01~11-03에 3일 연속 근무해 상한 2일을 초과했습니다 | 입력 오류, 기간 밖 이력 |
| R_FORBIDDEN_TRANSITION | 같은 간호사의 인접한 달력 날짜 전환 확인 | N,O 또는 E,D / N,D | 전날 N 다음 날 D는 금지 전환입니다 | 입력 오류, 기간 밖 이력 |

min_staff는 하한입니다. 초과 배정을 위반으로 보지 않습니다.
인원 검사는 requirements의 조합에서 시작하므로 실제 0명인 근무조도 반드시 남깁니다.
알 수 없는 ID나 중복 행이 있으면 인원 검사를 실행하지 않으므로 인원을 부풀리지 않습니다.
연속 근무·전환 검사는 파일의 행 순서가 아니라 날짜의 순서와 1일 간격으로 판단합니다.

기간 이전 이력이 없으므로 시작일 이전부터 이어진 근무와 시작일 전날→시작일 전환은 평가 범위 밖입니다.
종료일 다음 날로 이어지는 구간·전환도 알 수 없습니다.
PASS는 **기간 내부에서 평가 가능한 규칙을 통과했다는 뜻**이며 기간 밖까지 보장하지 않습니다.
이 한계는 정상 출력에도 범위 설명으로 남깁니다.

## 출력과 집계 단위

상세 결과에는 rule_id, file, row_numbers, nurse_id, date, end_date, shift,
actual, expected, reason을 가능한 범위에서 포함할 예정입니다.
줄 번호는 헤더를 1로 세고, 누락처럼 실제 행이 없는 사건에는 빈 칸을 사용합니다.
사례 파일명은 한 사건의 파일을 특정하는 데 사용하며, 줄 번호만으로 사례를 식별하지 않습니다.

- 중복: 중복된 간호사·날짜 **키 하나당 1사건**. 관련 줄은 모두 표시합니다.
- 누락: 없는 필수 조합 하나당 1사건. 근무 불가: 간호사·날짜 하나당 1사건.
- 인원 부족: 날짜·근무조 하나당 1사건. 특정 간호사의 책임이 아니므로 nurse_id는 빈 칸입니다.
- 연속 근무: 상한을 넘긴 **최대 연속 구간 하나당 1사건**. 초과한 날짜마다 중복 출력하지 않습니다.
- 금지 전환: 인접 날짜 쌍 하나당 1사건. date는 전환 후 날짜, end_date는 빈 칸입니다.

사건 수, 관련 CSV 행 수, 영향을 받은 간호사 수는 다릅니다.
현재 예상 집계는 **사건 수**이며 빈 nurse_id를 임의로 특정 사람에게 배정하지 않습니다.
첫 작은 자료는 위의 모든 입력 규칙을 테스트하지 않습니다. 미포함 규칙의 테스트는 구현 단계에서 차례로 추가합니다.
